### API 概览

沿用 save、recover、readRecord、listPending 及状态投影契约。UI 以完整当前操作身份决定结果归属；不能把任意成功回执当作当前输入已保存，也不能把较早的读取失败当作当前读取失败。

### 关键流程与失败边界

完整闭环是：冻结动作 → 呈现保存中 → 本机事务提交 → 接受同一动作结果 → 呈现待同步 → 允许继续记录；明确失败则保留输入与旧内容，原操作可重试；响应丢失则保留输入并核对原回执。

程序重新启动时重新读取本机事实及当前回执，不重放旧动作，不把本机成功升级为统一位置成功。当前没有网络服务，证明本闭环不依赖远端可用性；不据此声称真实同步或离线补同步已交付。

### 并发与状态保护

- 重试使用相同操作身份；一次写入失败后恢复环境，不能悄悄换成新动作。
- 丢失响应的真实已提交操作经过核对后只能接续原序号，不能形成第二条日志。
- 新草稿和旧回执各有身份；旧成功不能清空或标记新草稿。
- 并发刷新只接受最新读取请求的内容或错误；过期读取失败不能遮蔽新读取成功。
- 不同领域沿用相同保存闭环，但各自保留自己的载荷与归属，不引入待办字段作为公共模型。

### 验收证据

整合测试使用真实磁盘：正常保存与重试、数据库约束拒绝后的回滚与修复重试、提交后响应丢失与重启核对、不同领域的独立载荷。

窗口验收保留真实 IPC 和数据库路径，借助测试进程在独立数据库安装临时拒写 trigger，验证界面失败、保留输入、保留旧内容、删除 trigger 后重试和清空已提交输入。随后关闭整个 Electron 应用并重新启动，验证最新内容和待同步状态。故障仅存在于测试临时目录，生产宿主无故障开关。

实际验证：pnpm check 通过包依赖边界和 TypeScript 检查；Node.js 22.23.0 与 Electron 45.0.0 内置 Node 24.22.0 各通过 48 项（原 44 项与新增 4 项整合测试），真实窗口测试 2 项通过。追加的读取竞争回归也通过窗口测试，确保较早读取的异常不会覆盖较新结果。测试不访问用户数据目录。
