### API 概览

| 契约 | 方向与输入语义 | 输出语义 | 失败边界 |
|---|---|---|---|
| save | 调用方保留原操作 ID，传入原领域动作快照 | 首次提交或等价重试返回同一保存序号 | 同 ID 携带不同对象、领域、动作或载荷明确拒绝 |
| recover | 调用方提供原空间、领域、内容与操作身份，不提供新动作 | 只读取原提交回执，不改变当前内容 | 无回执或读取不可用时保持尚不能确认 |
| readOperation | 核心通过存储端口读取指定操作 | 返回不可变原提交材料或未找到 | 读取错误必须拒绝，不伪造未找到 |

字段与完整类型由 contracts 源码维护。回执只证明本机已保存；本节点不提供服务器确认，也不把回执序号当成当前内容进度。

### 数据模型与留存

沿用 N01 已提交操作日志：每条不可变快照及保存序号同时作为本机幂等回执。无格式迁移，已有 N01 数据可以直接重试和核对。

目前 pending_operations 同时承载待同步材料与回执，尚无发送后删除或队列清理接口。后续同步节点必须先实现独立回执留存或保留已确认日志，才能清理发送队列；不能因同步完成就丢掉去重依据。

空间内的操作 ID 唯一；内容 ID 和文字相同均不表示同一次操作。载荷按 JSON 值比较，忽略对象键顺序，保留数组顺序及类型差异。时间戳、设备时钟和文本相似度不参与去重。

### 关键流程

1. save 在发送前固定输入快照与操作身份。
2. 存储先读取同一操作回执；已存在且语义一致则直接返回原序号，不写当前记录。
3. 无回执时取得写事务，再次检查回执，防止并发连接都通过先前读取。
4. 仍不存在才执行 N01 的完整事务；已存在则核对并返回，不生成第二个操作。
5. recover 只读取原回执。未找到不能证明其他在途请求从未发生，因此保持 save-unconfirmed，不自动重发或新建 ID。

明确未保存时可以携原 ID 及快照再次 save；结果不明先 recover，再沿原身份处理。即使调用方误重发，同一事务的幂等门禁也不得重复执行。

### 状态与一致性

| 场景 | 结果及副作用 |
|---|---|
| 相同操作重复提交 | 相同保存序号，当前内容不重写 |
| 相同 ID 对应不同动作 | not-saved / operation-mismatch，保留原回执和内容 |
| 回执存在，但内容已继续修改或删除 | 返回原回执，保留较新内容或删除标记 |
| 核对未找到或读取失败 | save-unconfirmed，保留原操作身份，不主动写入 |
| 两次主动提交同一文字但 ID 不同 | 两次独立动作，不按文本合并 |

事务内二次核对和数据库唯一约束共同防止竞争重复。readOperation 的范围含空间、领域、内容和操作身份，不能因为同一个操作 ID 就返回另一领域材料。

### 异常处理

写失败并完整回滚后，原 ID 可重新提交。未知传输失败保留不确定结果；核对失败不能产生空回执成功。身份不匹配通过 worker 保留为独立类别，不变成普通存储故障后自动重试。

### 监控与测试

在真实磁盘验证：多次与并发重复提交、跨连接竞争、跨重启和进程终止恢复、响应丢失后读取、明确失败后原 ID 重试、删除动作、同 ID 不同载荷/对象/领域/动作拒绝、旧回执不覆盖较新状态、不同 ID 的同文内容以及只读核对。

本轮仍是本机能力；服务器去重、远端结果核对、界面阻塞和同步状态在对应后续节点接入时验收。

验证结果：包依赖边界与 TypeScript 检查通过；Node.js 22.23.0 和 Electron 45.0.0 内置 Node 24.22.0 各通过 30 项真实磁盘测试（含原 N01 的 17 项和 N02 的 13 项）。恢复演示入口为 scripts/demo-recovery.mjs，通过 pnpm demo:recovery 运行。
