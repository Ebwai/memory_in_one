# codebase-index Skill
> 代码仓库的索引系统以及相关规范

## 触发条件

- 寻找代码
- 了解代码仓库

## 代码仓库索引系统

### 核心组件介绍
#### PRD
- 位置：\docs\PRD.md
- 作用：描述代码仓库的PRD，回答「**产品应该是什么？（What）**」，聚焦**产品能力**，不讨论技术实现。包括代码仓库的痛点 -> 功能映射（需求拆解）； 概念和机制详细说明；交互流程和细节；边界情况与异常处理。其中概念和机制名称是代码仓库的索引系统中设计的锚点，通过搜索概念和机制名称，就能直接搜索到相关层级的Architecture类文件和TDD类文件（假如搜不到退回到顺着上层Archietcture在模块化以上的层级逐层找到概念和机制对应的代码的方案）。阅读PRD文档全文，特别是PRD完整骨架(需求→ 概念/机制映射)章节，可以快速掌握这个项目中所约定的一些术语、概念和机制的名称，以及从上层视角对每个概念、机制的理解。

#### Achitecture类
- 位置：由多个文件组成
  - 最上层：\docs\architecture.md
  - 下级不同层级：\.claude\rules\architecture\*
- 作用：从模块级别接管Architecture继续向更深入更详细的部分描述，一层一层的描述在当前这一层级的信息和下一层级的信息（不会跨越多层级），包括架构图，定位与职责，内部组成，依赖与联动，技术选型，非功能约束、非功能性约束；Architecture 类 回答「**系统应该如何组织？（System）**」，聚焦**系统架构**，不讨论接口细节和数据库细节（留到 TDD）
- 范围：从最上层到模块级（模块级以下的由TDD接管负责引导）
- 每篇Archiecture类文档内部的结构：架构图、定位与职责、内部组成、依赖与联动、技术选型、非功能约束（在开发中一般不会随着代码实测随时会变动的内容部分【一般只会由需求修改的时候往下传递才会变动】）

#### TDD类
- 位置：由多个文件组成
  - 最上层：\docs\TDD.md
  - 下级不同层级：\.claude\rules\tdd\*
- 作用：从最上层级别到模块级别，一层一层的描述在当前这一层级的本身的介绍和下一层级的东西（不会跨越多层级），包括模块架构图，模块概览，API概览，数据模型，数据模型，关键流程、状态机、异常处理、监控与测试；TDD 类 回答「每个模块如何实现？」，聚焦技术实现细节。
- 范围：模块级以下
- 每篇TDD类文档内部的结构：模块架构图、模块概览、API 概览、数据模型、关键流程、状态机、异常处理、监控与测试

### 检索流程

1. 首先阅读PRD的全文（即文档的PRD完整骨架(需求→ 概念/机制映射)部分），可以快速掌握这个项目中所约定的一些术语、概念和机制的名称，以及从上层视角对每个概念、机制的理解。
2. 找到与自己本次任务有联系的部分（或者自己比较疑惑的部分），确定几个关键词，然后搜索PRD，只详细读这些内容（非必要时不需要读PRD的全文）。了解本次任务所需要知道或能用上的概念和机制的详情和需求层面的设计细节
3. 尝试识别出锚点（PRD中的概念和机制名称），然后直接全库检索看能不能检索到相应层级的Architecture类文件或TDD类文件
如果检索不到或者返回的信息太多了，就换一种方法，顺着上层Architecture类文件在模块化以上的层级逐层找修改部分可能在当前层下的哪一部分，反复迭代，找到叶子节点，更细节的信息查看对应的TDD类文件。不要一次读很多文件，思考好了选择下一层，按需读即可，不用读很多文件。
