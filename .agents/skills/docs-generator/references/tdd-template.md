# TDD 模板 (Technical Design Document)

## 核心定位

TDD 回答「**在 Architecture 已确定的结构与边界内，关键行为如何实现？（Implementation Semantics）**」。

TDD 不承担“把最终代码预先用 Markdown 详细描述一遍”的职责，而是记录：

- 跨多个实现点才能成立的关键行为；
- 关键契约与状态的运行语义；
- 数据/状态/副作用如何协作流转；
- 一致性、并发、事务、幂等、失败恢复等非局部技术语义；
- 单个局部代码无法可靠恢复的重要设计意图；
- 指向真实实现的**实现锚点**，帮助 Coding Agent 从技术设计定位代码。

整体分工：

```text
PRD：What，产品能力与确定性业务规则
Architecture：Structure & Boundary，模块、职责、依赖、所有权
TDD：Cross-implementation Behavior & Semantics，多个实现点如何共同成立
Code-local Constraints：Local Invariants，单个定义附近必须满足什么
Executable Constraints：Enforcement，机器如何自动保证
```

> 核心判断：**维护一条技术语义必须同时理解多个实现点时，通常属于 TDD；只看一个模型/类/函数附近就能完整理解并维护时，属于代码附近。**

## TDD 生命周期：JIT Design

TDD 是 **Just-in-Time 技术设计**，不是 Architecture 完成后的全项目预设计。

新项目采用：

```text
PRD Baseline
→ Architecture Baseline
→ 某个原子需求进入实现
→ codebase-index 建立真实实现上下文
→ 按需生成 / 更新当前需求相关 TDD
→ Coding
→ As-built 校准 TDD
```

规则：

- Architecture baseline 完成后，不要求一次性补齐完整项目 TDD；
- 当前原子需求出现新的跨实现点技术行为时，才新增 / 更新 TDD；
- 如果当前需求完全复用已有技术行为，或仅涉及一个局部实现点，可以不新增 TDD；
- TDD 应在 Agent 已理解相关 PRD、Architecture、Existing TDD 和真实代码上下文后再设计；
- 实现完成后必须用 As-built 行为校准本次新增 / 修改的 TDD，删除已经被实现推翻的预想方案。

## 编写原则

1. **不重复 Architecture**：不重新画内部目录/模块拓扑，不重复职责树和所有权边界。
2. **PRD 业务语义不消失**：PRD 仍是确定性业务规则的产品层规范来源；TDD 只写这些规则如何形成跨实现点技术语义，不抄一份业务规则大全。
3. **导航信息要能落到代码**：TDD 的模块概览/API 概览应尽量提供实现锚点或事实源位置，使 Agent 能继续进入代码。
4. **不复制代码事实**：完整函数签名、完整字段 Schema、Migration、配置值、测试用例由其真实实现维护。
5. **局部规则下沉**：字段联合约束、条件必填、单函数前置/后置条件、局部 guard、单分支原因等放到代码附近。
6. **可执行优先**：关键规则能通过类型、validator、assertion、DB constraint、权限、静态检查或 tests 强制时，不只依赖自然语言。
7. **代码局部投影可以引用上游**：如果局部约束直接来自 PRD/TDD，可在代码附近用短引用标明来源；它是实现提醒/投影，不取代上游规范。
8. **只描述当前技术层级**：跨 Architecture 模块/所有权边界的规则提升到 Architecture；单定义规则下沉到代码。

## 章节结构（每个技术模块/设计对象一个 `##` 块）

### 每篇TDD文章开头都要按下面格式遵循项目实际路径填写front matter，填完了才再下面写接下来的架构图，定位与职责，... ，等等
```markdown
---
paths:
  - "<项目根相对路径>/**/*"
---

```

### 模块概览

这里只建立 TDD 的技术导航，不重复 Architecture 的模块职责树。

- **Architecture 位置**：对应的 Architecture block / 模块。
- **关联 PRD 概念/机制**：列出与本技术设计直接相关的 PRD 概念/机制名称，作为语义检索锚点。
- **本 TDD 关注的关键行为**：按需列出几个需要跨实现点理解的行为/技术问题。
- **核心对象/状态**：只列理解该行为必要的对象/状态名称。
- **实现锚点**：列出关键代码、Schema、Migration、配置或 test 的位置/符号，用于继续导航。

示例：

| 实现锚点 | 作用 | 事实源位置 |
|---|---|---|
| `OrderService.pay` | 支付行为入口 | `src/order/service.py` |
| `Order` | 核心状态对象 | `src/order/model.py` |
| `order_paid` event | 支付成功事件契约 | `src/order/events.py` |

> 新项目尚无代码时，不虚构路径；可写 `[待实现]` 或 `[待确认]`。

### API 概览（导航类 · 内容保留，会级联传递）

这里的 “API” 泛指需要多个实现点共同理解的稳定契约，包括：函数/方法边界、HTTP API、事件、消息、Tool、Resource、回调、Repository port 等。

| 契约 | 调用/消费方向 | 关键输入语义 | 关键输出语义 | 稳定失败类别 | 事实源位置 |
|---|---|---|---|---|---|
| `[名称]` | `[A → B]` | `[只写影响行为的语义]` | `[只写影响行为的语义]` | `[错误类别]` | `[代码/Schema]` |

规则：

- 不维护完整参数列表、字段表、默认值、枚举全集。
- 若具体参数值本身构成跨调用方兼容契约，可写其契约含义，但以真实 Schema/代码为细节事实源。
- 单个私有函数如果没有跨实现点契约意义，不需要为了完整列出。

### 数据模型（细节类 · 只留标题）

TDD 中的数据模型只描述**跨实现点理解所需的数据/状态语义**，不维护完整字段镜像。

可包含：

#### 1. 核心对象与所有权

| 对象 / 状态 | 所有者 | 语义角色 | 生命周期 / 可见范围 | 事实源位置 |
|---|---|---|---|---|
| `[名称]` | `[模块/组件]` | `[事实/投影/运行状态/DTO 等]` | `[创建→使用→销毁]` | `[代码/Schema]` |

#### 2. 事实源与派生关系（有则写）
如：
- 什么是 authoritative fact；
- 什么是缓存、投影、派生或可重建状态；
- 谁可以写、谁只读；
- 跨组件转换在哪里发生，以及转换是否改变所有权/语义。
等等

#### 3. 存储与事务语义（有则写）
如：
- 必须原子发生的变化；
- 明确不能放入同一事务的副作用；
- 非显然的查询/索引意图；
- Migration 的兼容/回填/回滚原则。
等等

**不要写：**

- 完整字段表；
- 每个字段的必填/default/min/max；
- `A > 0 → B != X` 一类单模型联合约束；
- 完整 DDL / Migration 脚本。

这些进入模型/Schema/validator/DB constraint/tests 与相邻 Code-local Constraints。

### 关键流程

只描述跨多个函数/组件、包含关键状态变化、副作用、一致性或恢复语义的流程。

每个流程建议包含（按需包含）：

- **关联 PRD 概念/机制**：使用名称建立追踪。
- **触发条件**。
- **参与实现点**。
- **主路径顺序**。
- **状态变化 / 副作用提交点**。
- **一致性 / 并发 / 幂等控制点**。
- **失败与恢复边界**。
- **最终可观察结果**。

可用 Mermaid 时序图。

不要把单个函数内部普通 `if/else` 或每行调用展开成流程文档。

### 状态机

仅当状态跨多个实现点、存在重要生命周期或对外形成稳定行为契约时填写。

记录：
如：
- 状态由谁创建、修改、持久化、读取；
- 跨实现点/外部可见的关键状态；
- 重要状态转换的触发与副作用；
- 哪些转换需要事务、CAS、锁、幂等或恢复保护；
- 状态定义和局部合法组合的代码事实源位置。
等等
可以使用简化状态表：

| 从 | 到 | 跨实现点触发条件 | 关键副作用 / 保护 |
|---|---|---|---|
| `[A]` | `[B]` | `[条件]` | `[副作用/事务/幂等]` |

单模型内部的合法字段组合和局部 guard 不在这里展开，写到模型/函数附近并由 tests/validator 保护。

### 模块级约束与不变量

只写**同一 Architecture 模块内部、多个实现点必须共同遵守**，且无法自然归属于单个定义的技术规则。

每条建议按需包含：

- **约束**：必须 / 禁止什么。
- **原因**：保护什么业务/技术性质。
- **涉及实现点**：哪些组件/函数族共同受影响。
- **上游语义来源**（如适用）：关联 PRD 概念/机制/规则名称。
- **保障方式**（如适用）：集成测试、权限、静态检查、运行时门禁等。

作用域变化时：

```text
跨 Architecture 模块 / 所有权边界 → 提升到 Architecture
多个实现点共同语义              → 保留 TDD
单模型 / 类 / 函数 / 分支         → 下沉到 Code-local Constraints
```

### 一致性、并发与幂等

记录模块级运行语义：
如
- **并发模型**：串行、并行、fan-out/fan-in、锁、乐观并发等。
- **一致性模型**：强一致、最终一致、快照、版本检查、CAS 等。
- **幂等边界**：哪些入口/副作用必须幂等，幂等身份由谁拥有。
- **冲突策略**：谁优先、何时重试、何时明确失败、保留什么证据。
- **恢复执行**：重复、乱序、进程恢复后必须保持什么性质。
等等
具体超时、重试次数和退避参数默认进入配置/实现；只有数值本身构成稳定契约时才记录。

### 异常处理

记录跨多个实现点才成立的失败语义：
如：
- 哪些失败可自动恢复，由谁恢复；
- 哪些失败必须阻止后续副作用；
- 哪些失败允许只读/部分降级；
- 恢复后必须重新验证什么；
- 对外需要保持哪些稳定错误类别。
等等
不要穷举异常类、错误文本或每个 `try/except` 分支。

### 监控与测试（如使用）

只按需记录**必须观察和证明什么**，不维护日志点和测试用例的逐条镜像。
如：
- **关键可观察事实**：哪些阶段、状态变化、副作用、失败原因必须可追踪。
- **审计边界**：哪些行为必须留下不可静默丢失的证据。
- **验证层次**：哪些性质由 unit / integration / E2E / 固定样例 / 静态检查 / 运行时校验保护。
- **关键不可破坏性质**：只列少量跨实现点性质；完整 tests 以测试代码为事实源。
- **实现锚点**：相关 observability / tests 的位置。
等等

### 关键技术决策

只记录未来难以从最终代码结果本身恢复的技术意图。

每项建议按需包含：
如：
- **决策**
- **备选**
- **原因**
- **后果 / 限制**
- **重评条件**
等等
如果决策改变模块边界、依赖方向、所有权或架构级非功能性质，应提升到 Architecture/ADR。

### 待确认事项

只保留确实影响技术设计、但当前输入无法确定的事项：

- `[待确认] ...`

不得为了文档完整虚构路径、字段、参数、阈值、Schema 或实现方案。

---

## 与 Code-local Constraints 的边界

TDD 只记录跨多个实现点才能完整理解和维护的技术语义。

如果一条约束只属于单个模型、类型、类、函数或局部分支：

- 不在 TDD 中详细展开；
- 按项目级 `.claude/rules/code-local-constraints.md` 维护在真实代码附近；
- 能机器保障时同步落实为 Executable Constraints。

如果约束作用域扩大：

```text
单定义 → Code-local
多个实现点 → TDD
跨模块 / 职责 / 所有权边界 → Architecture
产品行为 / 确定性业务规则变化 → PRD
```

具体 Code-local Constraint 的格式、放置、维护、升级和 Executable Constraint 规则由项目级 Rule 统一定义，本模板不重复维护。

---

## 最终约束

- TDD不是一篇文章，而是根据项目实际情况拆解出的多篇文章
- 不讨论产品价值；MRD/PRD 负责 Why/What。
- 必须遵守 Architecture 已确定的职责、依赖、所有权和跨边界约束。
- TDD 只保留关键行为与非局部技术语义，不下钻成完整代码字段/分支说明。
- Architecture baseline 完成后，不一次性预写完整项目 TDD；TDD 随 PRD 原子需求 JIT 设计并在实现后校准。
- PRD 的业务规则不因下沉代码局部约束而从 PRD 删除。
- 代码、Schema、Migration、配置、tests 是各自实现细节的事实源；TDD 用实现锚点连接这些事实。
- 不确定项标注 `[待确认]`，不虚构。
