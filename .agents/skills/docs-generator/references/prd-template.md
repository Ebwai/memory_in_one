# PRD
## 核心定位

PRD 回答「**产品应该是什么？（What）**」，聚焦**产品能力**，不讨论技术实现。

PRD 不只是最终需求文档，也是**需求逐层发现、与用户逐层对齐、最终收敛为 Concept / Mechanism 能力体系的产品事实源**。

用户最开始给出的需求可能非常粗糙，也可能已经夹带很多细节。无论初始输入有多完整，都必须遵循：

> **按层级逐步展开，不提前跳层；当前层只讨论当前层应该出现的内容。**

用户提前提到的深层细节不能丢失，但也不能因为用户已经提到，就在第一轮全部展开。应先记录为后续层级的已知输入，等递归到对应层级时再正式呼应、确认和补全。


## PRD类文档的组成

- 最上层PRD文档：位置在/docs/prd.md，主要存放PRD的完整骨架图，骨架图中的每一个节点是对应下面相应PRD类文档的引用
- PRD类文档：根据完整骨架图的层级结构，在/docs/prd/位置建立与之对应的文件夹。骨架图中的每一个节点都有一个相应的文档，存放在对应的文件夹位置，并被上层PRD文档中的骨架引用



## 需求发现与逐层对齐协议

正式形成 PRD 前，需求必须经过逐层 Requirement Discovery。
再拆解过程中的：
- **概念（Concept）**：表示用户直接看到和使用的功能。上一级概念是对下一级功能的概括与归类，概念之下可以继续拆出子概念，直至原子概念。
- **机制（Mechanism）**：用户不直接接触，但为实现概念、保障功能正常运行而存在的底层能力。机制也可以继续拆出子机制。只有确有需要时才拆出机制，不必为每个概念强行配套机制。
形成PRD完整骨架

### 1.从整体抽象逐层细化
先识别全部需求的共有含义和最高层的能力分类，用少量、颗粒度最粗的抽象节点覆盖整体需求，再经过多轮次逐层细化。

**每次只拆解当前节点的直接下一层，不跨层展开，也不一次性生成到底的完整结构。** 每轮围绕以下问题思考：

> 要让当前需求、概念或机制变得更具体，最直接需要拆成哪几个概念或机制？

各子节点应共同覆盖父节点的含义，明确各自的职责和边界，并且比父节点更具体。结合用户每轮的反馈，再继续展开选定节点。

越往上，节点越具有概括性，少量节点即可涵盖下面的多项能力；越往下，职责、行为和边界越明确，越接近技术落地，但无需讨论技术细节。

如无特殊要求，禁止第一次就跨越多层直接生成最终骨架图的全部。



### 2. 直接下一层的尺度

**同一父节点下的兄弟节点，应保持大致相当的细化程度，即相对于父节点向具体化推进的幅度相近**。概念与机制可以并列，但都应当是对当前父节点的直接细化。

这种尺度协调主要适用于同一父节点下的兄弟节点，不要求整棵结构中处于相同深度的节点具有统一的抽象程度。不同分支可以根据各自的语义范围和复杂度，采用不同的细化幅度与拆解深度；不要为追求形式一致而强行增加或压缩层级。

### 3. 用户提前给出的深层细节要“保留，但延迟展开”

用户的初始描述可能同时包含：

- 上层目标；
- 中层能力；
- 很具体的业务规则；
- 边界条件；
- 某个深层机制；
- 某个最终原子能力的细节。

这些信息都视为有效输入，但必须按其语义所属层级处理。

例如用户一开始说：

```text
“我要一个智能知识库，
外部 Agent 通过 MCP 查询，
更新时内部 Agent 要自动判断影响哪些文件，
如果人工同时修改要做三方融合，
融合不了保留人工版本。”
```

第一轮不能直接输出：

```text
智能知识库
├── MCP 查询
├── 影响范围发现
├── 三方融合
├── CAS
├── ...
```

而应先在当前层处理：

```text
智能知识库
├── Agent 知识查询
└── Agent 知识更新
```

同时记录：

```text
后续已知输入：
- 查询入口涉及 MCP
- 更新过程需要影响范围判断
- 存在人工并发修改场景
- 冲突需要融合且人工版本有保护要求
```

等拆解到：

```text
知识更新
→ 并发知识保护
```

这一层时，再正式呼应用户之前提到的“三方融合 / 人工优先”细节，并与用户确认其完整规则。

核心原则：

> **用户说得深，不代表当前就要拆得深；细节应该在它所属的层级被正式讨论。**

### 4. 每一层不仅复述用户，还要主动扩展用户认知

在每一层，都可以根据基于当前已经确认的能力主动提出（如适用）：
- 为了让当前能力成立，可能还需要什么前置能力；
- 是否存在用户没有提到的保障机制；
- 是否有常见边界情况；
- 是否有隐藏的状态、权限、一致性、异常或降级问题；
- 是否存在和其他 Concept / Mechanism 的复用机会；
- 是否存在两种以上合理产品行为，需要用户选择；
- 是否存在用户当前描述中隐含但尚未明确的能力。

这些内容必须作为：

```text
[建议]
[待确认]
```

提出，而不能直接写成已确认产品要求。

目标不是替用户做产品决定，而是通过逐层拆解不断扩展用户看到的问题空间，让用户在每一层都能被 AI 的拆解启发，再反过来补充、删除或修改需求


### 5. 当前层必须完成对齐后才能继续

每一层结束时，立刻更新PRD对应的内容（骨架+对应的文档新建【文件夹结构】），然后继续下一层

### 6. 原子节点与停止条件

持续拆解，直到当前需求范围内的原子概念或机制：**职责单一、行为及边界明确，能够独立说明、实现和验收，无须再拆成多个具有独立意义的功能。** 这里的“独立”指职责可单独界定，不代表运行时不能依赖其他节点。

不同分支可以在不同深度停止，不必追求层数一致。不要为了继续细分而把代码语句、底层调用或操作步骤机械地拆成功能节点。

### 7. 节点引用与功能包复用

任意层级的节点及其下属内容，都可以作为相应颗粒度的功能包复用。节点也可以引用其他子树中任意层级、语义适合的节点，无须重复定义或复制已有能力。

明确区分两种关系：

- **层级关系**：当前节点进一步拆成哪些组成能力。
- **引用关系**：当前节点需要使用哪些已在其他位置定义的能力。
    

复用一个节点时，应同时纳入其下属内容和必要的引用依赖；如果依赖节点还有必要依赖，也应沿引用关系继续纳入。纳入依赖不意味着复制节点，可以通过引用已有能力实现复用。引用应明确指向具体节点，避免含糊引用和循环依赖。整体结构不是强制成为严格树，而是类似于树+图的结构

### 8. 动态调整与公共能力抽取

拆解结构可以随着需求细化而演化，已有节点的位置、归属和拆解方式并非固定不变。

每轮拆解时，都应检查新增能力是否已在其他位置存在，或是否与已有能力具有可复用的共同部分：

- 已有节点能够满足需求时，直接引用。
    
- 某个节点逐渐被多个分支需要时，可将其从原有子树中抽取到语义和抽象层级合适的公共位置，由原分支及其他分支共同引用。
    
- 各处需求仅部分相同时，只抽取共有部分，差异保留在各自节点中。
    

必要时，可以移动、合并、拆分、重命名或重新归类已有节点，并同步更新相关引用，确保原有需求仍被完整覆盖。不要仅因名称相似就合并节点，也不要提前抽象尚未出现的共同需求。

**每轮仍以展开当前节点的直接下一层为主。** 如本轮发现需要调整已有结构，应向用户说明发现的共性、调整原因，以及调整后的归属和引用关系，使用户能够理解并参与结构的演化。

## 最上层PRD文档的内容模板

>将用户原始需求按照“需求发现与逐层对齐协议”逐步拆解，直到拆解到原子概念/机制（能力），为**多级结构**
一个需求可以由多个 Concept / Mechanism 满足，一个 Concept / Mechanism 也可以服务多个需求。

#### PRD完整骨架(需求→ 概念/机制映射)
- 骨架的意义： 包括所有概念和机制，因为PRD全部内容可能太长了，别人来阅读只能通过阅读PRD完整骨架来了解全局，然后定位下面的详细说明中所需的内容，并且类似于下面示例一样的结构进行书写
- 骨架可以动态调整：以下面的示例骨架为例：创建主题内的名称校验时→ 发现重命名也需要→ 抽取为 A，原分支与新分支均引用 A
- 骨架的每个节点都用mardown引用的格式`[[]]`写，新建对应节点的文档，并用`[[]]`引用其对应地址
- 每个节点的名字要没有歧义且唯一，比如可能有很多个地方有”新增“功能，但是需要加前缀

示例：

```text
{用户xx需求} ──→ [[文章收藏管理]] [C]
             ├── [[文章收集]] [C]
             │   ├── [[添加收藏]] [C]
             │   │   ├── [[填写收藏信息]] [C] ──→ ……
             │   │   ├── [[确认添加收藏信息]] [C] ●
             │   │   └── [[收藏输入校验]] [M]
             │   │       ├── [[链接格式校验]] [M] ●
             │   │       └── [[标题非空校验]] [M] ●
             │   └── ……
             ├── [[收藏组织]] [C]
             │   ├── [[创建主题]] [C]
             │   │   ├── [[填写主题名称]] [C] ●
             │   │   ├── [[确认创建主题名称]] [C] ●
             │   │   └── ⇢ [[{引用 A}]]
             │   └── [[重命名主题]] [C]
             │       ├── [[修改主题名称]] [C] ●
             │       ├── [[确认修改主题名称]] [C] ●
             │       └── ⇢ [[{引用 A}]]
             ├── [[收藏取用]] [C] ──→ ……
             └── [[收藏持久保存]] [M]
                 ├── [[收藏数据存取]] [M] ──→ ……
                 └── [[主题数据存取]] [M] ──→ ……

公共能力区 ──→ A：[[主题名称校验]] [M]
               ├── [[名称非空校验]] [M] ●
               └── [[名称唯一性校验]] [M] ●

图例：`[C]` 概念；`[M]` 机制；`●` 原子节点；`⇢` 引用；`……` 省略或待展开。树枝表示直接下一层
```
#### 完整骨架图节点的实现顺序推荐

根据骨架，bottom-up策略，优先实现可以被别人复用的概念或机制，给出一份所有节点的实现顺序排列
输出2个东西：
1. bottom-up的完整概念/机制骨架图（这个和上面骨架图的形式类似，是一个类似于树，但是也有类似于图中节点连接的结构，区别在于这里没有需求，而是体现不同概念/机制之间的依赖关系。）
2. 一行一行表示的实现顺序
PS：在排列的时候，不止是原子叶子节点参与排，而是每个节点多参与排列。不只是去实现原子功能，而是最终要回归到上级的功能包

## PRD类文档的内部内容模板
> 这个是骨架中引用的每一个文档中的内容，主要写对每个 Concept / Mechanism 描述
- **功能描述**：这个概念/机制是什么。
- **定位**：自己的节点+自己节点以下的局部骨架图
- **业务规则与约束**：所有确定性产品规则，例如：
  - “订单完成后 7 天内可评价，超时关闭入口”
  - “评价最多上传 9 张图”
  - “敏感词内容进入人工审核”
- **交互流程和细节**：对需要用户直接参与的 Concept，描述实现核心功能的完整产品路径，不讨论函数、接口、数据库或实现组件：
	- **核心动作的完整路径**：从入口到完成的步骤；
	- **前置条件**；
	- **交互反馈规则**；
	- **关键分支**；
	- **用户可观察结果**。
	- 案例：
		- ```
### 概念 [名称] 的交互流程
		
		**前置条件**：
		- [条件1]
		- [条件2]
		
		**主流程**：
		1. 用户 [动作1] → 系统 [反馈1]
		2. if [条件] → [动作 / 反馈]
		3. elseif [条件] → [动作 / 反馈]
		4. ...
		  ```
- **数据范围**（如适用）：涉及哪些产品数据、数据从哪里来。
- **前置能力**：该能力成立依赖哪些其他 Concept / Mechanism。
- **边界情况与异常处理**：这里写的是产品应该表现成什么，不写技术恢复方案
	- **边界情况**
	- **异常处理**
	- **降级策略**
	- **用户 / 上层能力应该看到的结果**


## PRD文档的更新流程

相当于来了一个新的需求需要遵循”需求发现与逐层对齐协议“逐层拆解，更新骨架图和对应的文档（对于骨架图是多一个{用户xx需求} ─起点开始拆解）。只是比初次构建的时候多了很多已经有了的功能包节点（概念/机制），可以看能不能复用现有的或修改或补充现有的节点设计，从而快速高效的实现新需求的实现开发，减轻工作量，但是也不能一味的为了提高复用性而去破坏现有软件的设计哲学和架构设计理念
### 更新的KeyPoints
#### 最小新增原则

面对每个能力 / 新需求，依次判断：

1. 已有功能包能否直接满足？
2. 能否通过多个已有功能包组合满足？
3. 是否只需要扩展某个已有功能包？
4. 如何在满足新需求的情况下，充分复用现有功能？
5. 最后才新增新的 Concept / Mechanism。

不要为了每个用户需求创建一套互相重复的产品能力。

此章节只讨论**产品能力依赖 / 复用**，不讨论：

- 模块依赖；
- class / function；
- API；
- DB；
- 技术调用关系。

这些留给 Architecture / TDD。
