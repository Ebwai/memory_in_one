# Architecture Design 模板

## 核心定位

Architecture Design 回答「**系统应该如何组织？（System）**」，聚焦**系统/目录/模块的结构、职责、依赖、所有权与跨边界约束**，不讨论接口字段和函数内部实现细节。

Architecture 在整个知识体系中的职责：

```text
PRD：产品应该是什么（What）
  ↓ 提供概念 / 机制 / 业务语义锚点
Architecture：系统如何组织（Structure & Boundary）
  ↓ 确定模块、职责、依赖、所有权和跨边界规则
TDD：关键行为如何在既定边界内实现（Cross-implementation Semantics）
  ↓ 指向真实实现
Code-local Constraints：单个定义附近的局部成立条件
Executable Constraints：类型 / validator / guard / DB constraint / tests 等自动保障
```

Architecture 的核心作用不仅是描述结构，也是给人和 Coding Agent 提供**宏观代码导航地图与全局 reasoning context**：

- 这个 PRD 概念/机制由哪些模块承接；
- 当前层有哪些直接组成部分；
- 每个部分负责什么、不负责什么；
- 谁依赖谁、通过什么方式协作；
- 数据、状态、事实与关键副作用由谁拥有；
- 修改一个模块时，还必须考虑哪些相邻模块与跨边界约束。

Architecture **不负责**描述一个关键行为内部逐步如何实现，也不记录字段级、函数级、分支级业务约束。

> 核心判断：**描述“东西放在哪里、谁负责、谁依赖谁、谁拥有状态/副作用、跨模块什么不能破坏”时写 Architecture。**

## 编写原则

1. **只描述下一级**：当前块只描述直接子模块/子文件夹，不越级展开更低层级结构。
2. **PRD 锚点用于导航，不复制 PRD 细节**：Architecture 可写关联的 PRD 概念/机制名称，使 Agent 能通过名称检索到责任模块；不要重复完整业务规则与交互说明。
3. **结构事实只在 Architecture 维护**：目录组成、模块职责、依赖方向、所有权不在 TDD 再维护一份镜像。
4. **边界优先于实现**：描述允许/禁止的依赖、所有权和协作边界，不描述函数内部步骤。
5. **只有跨边界规则进入 Architecture**：单模块内部多个实现点共同遵守的规则进入 TDD；单模型/类/函数规则进入代码附近。
6. **可执行优先**：能由依赖检查、权限、静态检查或集成测试验证的架构规则，应尽量可执行化。
7. **引用而非复制**：API Schema、数据库 Schema、Migration、配置、测试等只记录事实源/锚点，不复制完整内容。
8. **Architecture 既是导航，也是实现阶段的全局约束**：Agent 定位到代码后仍应保留已读取的 Architecture 边界作为修改方案的复核依据。

## 章节结构（每模块/文件夹一个 `##` 块，以下为各维度 `###`）

### 每篇Architecture文章开头都要按下面格式遵循项目实际路径填写front matter，填完了才再下面写接下来的架构图，定位与职责，... ，等等
```markdown
---
paths:
  - "<项目根相对路径>/**/*"
---

```

### 架构图

- 用 **Mermaid** 描述该文件夹内部**直接子模块**的组织关系和依赖拓扑。
- 只展示本级直接子模块之间的关系。
- 图中节点 = 下一级文件夹/模块���边 = 依赖、调用、事件订阅或主要数据流方向（边上要有字描述连接二者之间的关系）。
- 不枚举普通实现文件，不画函数调用图，不把 TDD 的流程图搬到这里。


### 定位与职责

- **职责**：这个模块/文件夹的稳定技术职责是什么（一句话）。
- **关联 PRD 概念/机制**：列出本模块直接承接的 PRD 概念/机制**名称**，用于语义检索；只写名称或最短说明，不复制 PRD 规则。
- **边界**：
  - 负责：[本模块拥有的能力、状态或副作用]
  - 不负责：[明确由其他模块拥有的事项]
- **所有权**（有则写）：本模块拥有的事实、运行时状态、资源或关键副作用。

> 同一个 PRD 概念可以由多个模块共同承接；Architecture 负责明确各模块分别承担哪部分技术职责。

### 内部组成

- 列出当前模块/文件夹的**直接**子模块或子文件夹。
- 每个子模块只写一句稳定职责。
- 可附其主要关联的 PRD 概念/机制名称，帮助继续向下检索。
- 普通文件没有独立架构职责时，不为了“完整”逐文件枚举。

### 依赖与联动

- **内部子模块间依赖**：谁依赖谁，必要时明确禁止方向。
- **通信方式**：同步调用、异步消息、事件总线、IPC、文件/数据库等。
- **数据与状态流**：主要数据/状态如何跨模块流动，在哪里发生所有权或格式边界；不展开字段映射。
- **副作用边界**：哪些子模块有权执行持久化、外部调用、发布、删除等关键副作用。
- **关键交互场景**：最重要的 2–3 个跨子模块场景，只描述参与者、方向和边界；详细执行步骤进入 TDD。

### 架构级约束与不变量

有则写，无则省略。只记录影响**多个直接子模块、所有权边界或系统边界**，且不能可靠归属于某个单一实现点的规则。

每条建议包含：

- **约束**：必须 / 禁止什么。
- **保护目标**：它保护的架构性质是什么。
- **作用范围**：涉及哪些模块/边界。
- **保障方式**：依赖检查、权限、静态规则、集成测试、运行时门禁等。
- **来源**（如适用）：关联的 PRD 概念/机制或上层 Architecture 决策名称；不复制完整上游正文。

示例：

- 派生投影不得反向覆盖事实源。
- 非事实所有者不得绕过领域端口直接写事实存储。
- 业务模块只能产生结构化领域事件，不直接拥有 observability 持久化状态。

作用域判断：

```text
跨 Architecture 模块 / 所有权边界 → Architecture
单模块内部多个实现点共同成立       → TDD
单模型 / 类 / 函数 / 分支           → Code-local Constraints
```

### 技术选型

有则写，无则省略。只记录对当前架构层级有**结构性影响**的技术选择。

- **技术**：选用的技术/框架/库。
- **用途**：在本层架构中承担什么角色。
- **选型理由**：为什么选它而非替代方案。
- **替代方案**：考虑过但未选的方案及原因。
- **边界影响**：形成了什么依赖、部署、状态、可替换性或平台约束。

单个函数或局部算法使用什么库，通常不进入 Architecture。

### 非功能约束

有则写，无则省略。描述当前架构层级必须保证的非功能性质及责任归属，不填写局部实现参数。

可包含：

- **解耦性 / 可维护性**
- **可靠性 / 一致性**
- **安全性 / 权限边界**
- **可扩展性（Scalability）**
- **可观察性（Observability）**
- **跨平台（Cross-platform）**
- **性能边界**（只有架构级目标或预算时）

具体超时、重试次数、阈值、日志格式等进入 TDD、配置或实现；只有具体值本身是系统级契约时才写 Architecture。

## Architecture 与其他层级的交界

### PRD → Architecture

PRD 是产品语义的规范性来源，尤其是：

- 概念（Concept）名称；
- 机制（Mechanism）名称；
- 产品能力；
- 确定性业务规则；
- 用户流程、边界与异常产品语义。

Architecture 使用这些名称作为**语义锚点**，把它们映射到技术责任与模块边界，但不重新解释产品规则。

### Architecture → TDD

Architecture 交给 TDD 的是已经确定的结构边界。TDD 不应重新维护：

- 模块/目录有哪些直接子模块；
- 每个子模块的稳定职责；
- 基本依赖拓扑；
- 状态/事实/副作用的架构级所有权；
- 已确定的跨模块架构不变量。

TDD 继续回答：

- 关键契约承担什么运行语义；
- 一个关键行为如何跨多个实现点完成；
- 核心状态如何流转；
- 事务、一致性、并发、幂等和恢复如何协作；
- 模块内部有哪些非局部技术不变量。

### Architecture / TDD → Code-local Constraints

字段联合约束、条件必填、单函数 guard、单定义合法状态组合、局部算法假设等默认不进入 Architecture/TDD 的详细正文，应放到相关代码附近并尽量可执行化。

## 最终约束

- Architecture不是一篇文章，而是根据项目实际情况拆解出的多篇文章
- **不讨论 API 细节**：不定义具体 API 签名、参数列表、返回字段；关键契约行为语义由 TDD 负责。
- **不讨论数据库字段细节**：不定义完整表结构、字段类型、索引或 Migration 内容；存储语义由 TDD 衔接，细节以 Schema/Migration 为事实源。
- **不复制 PRD 业务规则**：只通过概念/机制/规则名称建立可检索映射。
- **不讨论产品价值**：由 MRD/PRD 负责。
- 聚焦系统/目录/模块的组织结构、职责、依赖、所有权和跨边界约束。
- **只描述下一级，不越级。**
- 不确定且影响架构决策的信息标注 `[待确认]`。
